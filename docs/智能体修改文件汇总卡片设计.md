# 智能体修改文件汇总卡片设计

> 状态：一期已实现，未提交（2026-10-28）。实现与原稿的出入见第 11 节；后续改动如需偏离，先改本文再改代码。

## 1 背景与目标

现状：智能体运行时，每次写入都在执行时间线里插入一张完整的提案卡片；运行结束后，这些卡片统一挪到回复下方的 `approval-card-stack`，并且**默认收起**，只在消息操作栏留一个小箭头。结果是：

- 用户看不出这一轮到底改了哪些文件、改了多少；
- 请求审批模式下，待审提案也被一起藏起来，容易漏审；
- 展开后又是一摞大卡片，每张都带完整头部和差异，文件一多就很长，信息分散。

目标：运行结束后，把本轮所有修改汇总成**一张“修改文件”列表卡片**。卡片始终可见，一行一个文件，显示名称、增删行数和状态；点击某一行，就地展开看修改内容和审批操作。

不做：改提案数据、契约、Main 或 Core。本方案只改 Renderer 的展示层，审批、撤销、定位全部沿用现有事件与 coordinator。

## 2 现状与代码位置

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 本轮提案汇集 | `components/conversationToolPresentation.ts` 的 `approvalItemsForMessage` | 合并 `message.editProposals`、本轮长篇提案、远端设备提案，按时间排序 |
| 运行中 | `liveTimelineItems` → `ConversationProcessingTimeline` → `ConversationProcessingItem` | 提案卡片锚定在触发它的工具调用后面，可以边跑边审 |
| 运行结束 | `ConversationMessageItem.vue` 的 `approval-card-stack` | 卡片挪到回复下方，`approvalCardsExpanded` 默认 `false`，即默认隐藏（10-23 的 5823121b 由“默认展开”改成“默认收起”） |
| 短篇/剧本/资料库卡片 | `AgentEditProposalCard.vue`（489 行）+ `AgentEditProposalDiff.vue` | 头部（标题、状态、定位、撤销、增删数）+ 差异（又一层折叠）+ 底部审批按钮 |
| 长篇卡片 | `LongProposalReview.vue`（1001 行，`conversation-card` 模式） | 一个事件可含多个文件；内容类差异在组件内用 `buildAgentTextDiff` 现算 |
| 同一文件多次写入 | `utils/agentEditReview.ts` | 以 `laneId`（run + 作品 + 阶段 + 文档）为逻辑目标；上一代待审时原地合并，已决定后才生成新一代。自动审批下同一章写 3 次就会有 3 张卡 |

## 3 关键决定

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | 汇总卡片始终显示，不再默认隐藏 | 去掉操作栏里的展开箭头；卡片头部本身可收起，用户的选择按消息记住 |
| 2 | 一行一个“修改目标” | 短篇按 `laneId` 归并，同一文件多次写入只占一行；长篇按审批单元（一个事件）占一行，含多个文件时行内注明文件数 |
| 3 | 需要用户处理的行默认展开 | 待审阅、冲突、失败、“你修改过”这几种状态默认展开，其余默认收起 |
| 4 | 状态变化不重排、不自动收起 | 行的顺序按首次写入时间固定；接受后行保持展开并就地显示“已保存”，避免列表跳动 |
| 5 | 展开内容复用现有卡片逻辑 | 审批按钮、状态文案、撤销、定位全部来自现有组件，不复制一套判断 |
| 6 | 运行中保持现状（已确认，方案 A） | 一期只改运行结束后的展示，运行中仍在时间线里逐张显示、可边跑边审 |

## 4 交互设计

### 4.1 卡片结构

```
┌──────────────────────────────────────────────────────────────┐
│ ▾ 修改了 4 个文件                    +128 −36   ● 1 项待处理 │  ← 头部，点击收起/展开列表
├──────────────────────────────────────────────────────────────┤
│ ▸ 📄 第三章 · 正文                  +42 −8         已接受 ↗ │  ← 收起的行，↗ 为“跳转到目标文件”，悬停/聚焦时出现
│ ▾ 📄 林晚 · 人物设定                +20 −3         待审阅    │  ← 需要处理，默认展开
│   │ 补充了林晚与师门决裂的动机，并修正年龄。                 │
│   │ ┌ @@ -12,4 +12,9 @@ ─────────────────────────────────┐ │
│   │ │ 12 12   林晚，二十三岁……                            │ │  ← 差异直接展示，不再嵌套“查看修改”
│   │ │    13 + ……                                          │ │
│   │ └─────────────────────────────────────────────────────┘ │
│   │ 接受后写入当前文稿。                  [拒绝] [接受并保存] │
│ ▸ 📄 第四章 · 正文   写入 3 次      +61 −25        已接受 ↗ │
│ ▸ ✦ 新建章节「第五章」                             已接受 ↗ │  ← 结构操作，无增删数
└──────────────────────────────────────────────────────────────┘
```

收起后的头部只剩一行：`▸ 修改了 4 个文件  +128 −36  ● 1 项待处理`。

### 4.2 头部

- 标题：`修改了 N 个文件`。N 为本轮涉及的文件数（长篇一个事件含 2 个文件就算 2）。只有结构操作时改为 `本轮有 N 项修改`。
- 合计增删：所有可统计行的增删之和；结构操作和远端无差异的行不计入。
- 状态摘要（右侧，一个点 + 文字，按优先级只显示最重要的一项）：
  1. `N 项待处理`：待审阅、冲突、失败、“你修改过”；
  2. `正在保存`：接受中、自动保存排队、长篇校验或等待前置文件；
  3. `已全部保存` / `已保存 N 项，放弃 M 项`（拒绝与撤销都算放弃）：全部已决定；远端设备待审时显示“在某设备上待审核”。
- 点击头部切换列表收起。状态存在 `${messageId}:file-changes-collapsed`（默认展开）。

### 4.3 行

收起时一行显示：

| 位置 | 内容 |
| --- | --- |
| 图标 | 文本修改用 `file`，结构操作（新建/重命名/删除章节、剧情结构、人物结构、长篇结构批次）用 `wand`，连续性账本归档沿用现有图标 |
| 标题 | 提案标题（如“第三章 · 正文”）；资料库条目附“素材库 · 库名”；长篇多文件事件写“林晚 · 2 个文件” |
| 标签 | `新建`、`删除`（删除用危险色文字，不用红底）、`写入 3 次`、`来自某设备` |
| 增删 | `+a −d`；同一行多次写入时见第 5.3 节 |
| 状态 | 沿用卡片现有状态文案与配色：待审阅、保存中、已接受、已拒绝、已撤销、内容冲突、保存失败、你修改过、待自动保存 |
| 定位 | 已接受的行在悬停或键盘聚焦时显示“跳转到目标文件”图标按钮，不必先展开 |

展开后显示（顺序固定）：

1. 修改说明（`proposal.summary`）；
2. 差异：直接展示，不再套一层“查看修改”折叠；大差异仍按现有 `truncated` 提示；
3. 长篇的结构与关联影响（现有 `long-proposal-impact`）；
4. 底部：状态说明 + 现有审批按钮（拒绝 / 接受并保存 / 保留我的 / 用智能体版本覆盖 / 重试），已接受时为“跳转到目标文件”和“撤销这次修改”。

整行头部是一个按钮（`aria-expanded`、`aria-controls`），键盘 Enter/Space 可切换；“跳转到目标文件”按钮阻止冒泡，不触发展开。

### 4.4 默认展开规则

- 行的展开状态存 `${messageId}:file-change:${rowKey}`，**用户点过就以用户为准**。
- 用户没点过时：行在“需要处理”状态下展开，其余收起。规则在每次渲染时按当前状态求值，但一旦行被渲染为展开，就把它记为已展开，之后状态变成“已保存”也不自动收起（决定 4）。
- 历史消息重新打开时按同一规则：已全部决定的轮次只显示列表，不展开任何差异。
- 折叠内容用 `v-if` 懒渲染（`ConversationDetails` 已是这样），收起的行不生成差异 DOM。

### 4.5 文件很多时

- 超过 8 行时只显示前 6 行，末尾一行 `还有 N 个文件` 点击后全部显示；
- 但只要有任何一行需要处理，就直接全部显示，避免待审项被折进“其余”里；
- 不做行内滚动容器，避免与对话滚动嵌套。

### 4.6 视觉

- 外层沿用 `edit-proposal-card` 的边框、圆角和 `--surface-raised`；行之间用 `--theme-line-soft` 分隔，悬停 `--surface-hover`，展开行的内容区用 `--surface-main`。
- 增删数沿用 `.is-addition` / `.is-deletion`；状态点与文字沿用 `edit-proposal-status` 的配色。
- 主操作按钮沿用中性深色实心按钮；“撤销这次修改”沿用 `ApprovalDiscardButton`。
- 跟随“设置 → 外观”的主题、强调色、字号即时变化；不写固定高度，最大字号下标题省略号截断、增删数和状态不换行。

## 5 数据归并

新增纯函数模块 `components/conversationFileChanges.ts`，输入 `approvalItemsForMessage` 的结果，输出卡片数据。不读 store，不做副作用，便于单测。

```ts
type FileChangeRowStatus =
  | "action"      // 待审阅、冲突、失败、你修改过
  | "progress"    // 接受中、自动保存排队、长篇校验/等待
  | "accepted" | "rejected" | "discarded";

interface FileChangeRow {
  key: string;                  // 行键，见 5.1
  kind: "text" | "structure" | "ledger";
  title: string;
  fileCount: number;
  tags: Array<"create" | "delete" | "remote">;
  writes: ApprovalCardItem[];   // 同一目标的各代，按时间正序；最后一个是当前可操作的一代
  additions?: number;           // 结构操作和远端无差异时为空
  deletions?: number;
  status: FileChangeRowStatus;
  firstCreatedAt: string;       // 排序依据，状态变化不影响顺序
}

interface FileChangeSummary {
  rows: FileChangeRow[];
  fileCount: number;
  additions: number;
  deletions: number;
  actionCount: number;
  progressCount: number;
  acceptedCount: number;
  rejectedCount: number;
}
```

### 5.1 行键

| 来源 | 行键 |
| --- | --- |
| 短篇/剧本/资料库提案 | `edit:${agentEditProposalLaneId(proposal)}` |
| 长篇提案事件 | `long:${event.id}`（一个事件是一个审批单元，不拆） |
| 远端设备提案 | `remote:${proposal.id}`（远端没有文档 ID，不归并） |

### 5.2 行状态

取该行**最后一代**的状态映射；`staleBase` 且待审阅视为 `action`；短篇自动审批下的“等待自动保存”视为 `progress`；`discardState` 为 `discarded` 时为 `discarded`，撤销中、撤销冲突、撤销失败分别归 `progress` / `action` / `action`。映射表与现有卡片的 `proposalVisualStatus`、`contentProposalVisualStatus` 共用同一份逻辑（见第 6 节的抽取），避免两边漂移。

### 5.3 同一文件多次写入

- 行头增删：一期显示各代**累计**值，并带 `写入 3 次` 标签，悬停提示“累计 3 次写入”；
- 展开后：先显示最后一代（带审批按钮），下方 `更早的写入（2）` 折叠区按时间倒序列出前几代，各自只读显示状态和差异；
- 二期：短篇文本提案在首代有 `discardSnapshot.beforeText`、末代有 `proposedText` 时，用 `buildAgentTextDiff` 算出**本轮净变化**作为默认差异，行头增删改为净值；条件不满足（含拒绝的代、长篇、结构操作）时退回一期展示。

### 5.4 长篇差异统计

`LongProposalReview` 现在在组件内对每个文件跑 `buildAgentTextDiff(beforeText, afterText)`。汇总卡片收起时也要显示增删数，因此把这段抽成按 `event.id` 缓存的纯函数（同一事件对象只算一次），卡片与汇总共用；行收起时只用统计值，不渲染差异。

## 9 风险与边界

- **长篇提案的生命周期：**长篇提案项来自 `longProposalItems` 队列，重启后是否还在取决于现有持久化；汇总卡片只展示当下能拿到的项，不另存数据。
- **大差异性能：**收起的行不渲染差异；长篇差异统计按事件缓存；短篇沿用已算好的 `additions` / `deletions`。
- **抽取 presentation 的回归：**两张卡片的状态文案分支很多，抽取时先把现有分支原样搬走并补快照式断言，再接入汇总卡片。
- **聊天等扩展智能体：**它们不产生提案，不会出现汇总卡片。

## 10 已确认结论（2026-10-28）

1. 运行中保持现状（方案 A）：卡片锚在对应工具调用后、可边跑边审；结束后收进汇总卡片。
2. 同一文件多次写入：一期用“最后一次 + 更早的写入”，净变化放二期。
3. “全部接受 / 全部拒绝”放二期。
4. 手机端（deepwrite-app）暂不改，桌面端一期先行。
