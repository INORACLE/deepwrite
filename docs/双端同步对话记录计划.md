# 双端同步对话记录计划

> 状态：2026-10-12 起草；同日确认第 3 节：D2 默认关闭，D3、D4、D7 按推荐，D8「初始化本机」本期不做，其余按推荐执行。同日两端实现 M0–M4，未提交，实现记录与验证见第 11 节。涉及桌面（本仓库）与手机（`deepwrite-app`）两个仓库，必须同时实现、同时发布。

> 一句话：在「同步范围」里新增「对话记录」分组，按作品开启后，短篇、剧本和长篇的智能体历史会话在电脑和手机之间互相同步，可以阅读，也可以接着聊。两端的会话存储和消息结构差别很大，所以不直接搬运各自的存储文件，而是定义一份两端共用的交换格式，在独立的同步通道里按“只增不减的并集 + 显式删除标记”合并，不进入现有的三方合并和冲突处理。

## 1 背景与目标

现在两端都明确把会话排除在同步之外：

- 桌面 `packages/contracts/src/device-sync/value.ts` 的 `safeSyncFile` 排除 `conversation.json`、`agent`、`transactions`；
- 手机 `docs/device-sync.md` 写明“会话、追加事务、Agent 私有状态……不进入同步内容”，接收作品时写入空会话（`book-projection.ts` 的 `importSyncBook`、`mobile-workspace.ts` 的 `write`）；
- 「初始化本机」后手机会话为空。

一期目标：

- **同步范围可选**：「同步范围」新增「对话记录」分组，列出每个已同步的短篇、剧本和长篇，可单独开启，组头三态全选。默认关闭。
- **双向互通**：电脑上的历史会话出现在手机的历史列表里，反过来也一样；删除、恢复会话也会传到另一端。
- **可读**：用户消息、回复正文、思考过程、工具调用摘要、提案摘要、子智能体摘要都能在另一端看到。
- **可续聊**：在另一端打开同步来的会话，可以继续发消息。两端都用消息的 `role` + `content` 重建模型上下文，所以同步正文就够续聊；上下文压缩的差异见第 10 节。
- **不打扰**：会话不产生“两端都有修改”的冲突卡片，也不需要逐项“采用远端/本地”。
- **旧版本不受影响**：未升级的一端照常同步作品、资料和模型配置，只是看不到对话记录。

一期不做：

- 素材库、技能库聊天，未选作品时的通用会话，「更多功能」里的聊天和各类分析；
- 附件正文与图片、评测快照、未发送的输入草稿；
- 在另一端接受或拒绝来自原设备的待审核提案；
- 实时同步、后台自动同步；
- 「仅同步最近 N 天」之类的历史裁剪（见 D7）；
- 「初始化本机」带上会话（放二期，见 D8）。

## 2 现状对照：两端的会话为什么不能直接互传

### 2.1 存储

| 项 | 电脑 | 手机 |
| --- | --- | --- |
| 位置 | Core 进程里的 SQLite（`utilities/conversation-storage/schema.ts`，`node:sqlite`），全局一个库 | 每个作品目录里的 `conversation.json`（V5 根指针）+ 内容寻址分块（`src/core/conversation-storage.ts`） |
| 作品与会话的对应 | 作用域键：短篇/剧本 `<workspaceId>:chat`，长篇 `long:<encodeURIComponent(bookId)>:chat`（`bookConversationKey.ts`），再编码成 `conversation-history:…` | 一个作品一个文件：当前会话 + `history` 数组 |
| 作品 ID | 与同步条目 ID 相同 | 短篇/剧本可能是 `book_import_<hash>`，要经 `.deepwrite-project-sync-identity.json` 换成同步用的 `portableId`；长篇与电脑一致 |
| 写入方式 | Renderer 持有已加载会话，按批次（`ConversationHistoryBatch`，带 `expectedRevision`）提交给 Core | 状态层持有会话，2 秒防抖整体保存，保存时合并已提交事实 |
| 删除 | 软删除（归档），可在「已归档会话」恢复，另有彻底清除 | 直接删除 |

### 2.2 会话

| 字段 | 电脑 `AgentConversationPersistenceRecord` | 手机 `conversationSessionSchema` |
| --- | --- | --- |
| ID | `sessionId` | `id` |
| 时间 | `createdAt`、`updatedAt` | 同 |
| 本机设置 | `draft`、`approvalMode`、`temperature` | `selectedModelId`、`agentTeamMode` |
| 当前会话 | 快照级 `activeSessionId` | 顶层 `activeSessionId` + 当前会话字段平铺在根上 |

### 2.3 消息（不适配的主要来源）

| 内容 | 电脑 `ChatMessage`（宽松解析，未知字段丢弃） | 手机 `chatMessageSchema`（严格，未知字段拒绝） |
| --- | --- | --- |
| 状态 | `streaming / completed / stopped / error`（读回时 streaming 视为 stopped） | `streaming / complete / cancelled / error` |
| 错误 | `errorMessage` 字符串 | `error: { code, message, status? }` |
| 模型 | `runtime: { provider, model, mode, configId? }` | `modelConfigId`；会话级 `selectedModelId` |
| 思考 | `thinking` 字符串 + `processingSteps` | `agentEvents` 里的 `thinking-delta` + `processingSteps` |
| 工具 | `toolCalls`（`AgentToolTrace`，含参数）+ `tools` | `agentEvents` 的 `tool-start / tool-end`（只有摘要） |
| 提案 | `editProposals` 内嵌在消息里：差异块、`proposedText`、`discardSnapshot.beforeText`、电脑端文档/阶段 ID | `proposalIds`、`libraryProposalRefs`，提案存在单独的提案库里 |
| 子智能体 | `subagentRuns`、`subagentDraws`（含思考、输出、工具轨迹） | `agentEvents` 里的子智能体进度事件 |
| 上下文压缩 | `contextCompactions`，含 `checkpoint` 摘要 | 没有，按本机窗口截取历史 |
| 附件 | 只有元数据 `{ id, name, kind, mediaType, size, truncated? }` | 文本附件含正文，图片指向本机文件，续聊时会读取图片 |
| 仅电脑 | `usage`、`contextTokens`、`retry`、`activityOnly`、`evaluationSnapshot`、`processingStartedAt/CompletedAt` | — |
| 仅手机 | — | `generationTarget`（手机文档 ID）、`appendedAt` |
| 消息 ID | `<前缀>_<8 位十六进制>`（`@deepwrite/shared` 的 `createId`，只有 32 位随机） | `Crypto.randomUUID()` |

### 2.4 同步引擎

- 提交记录 `syncCommitSchema` 是严格 Schema，`kind` 是固定枚举。旧版本读到含新 kind 的提交时 `readCommit` 返回空，最后报“设备同步记录无法验证”，**整个同步都会失败**，不只是跳过一项。
- 基线、祖先和「历史与恢复」都保存条目的完整副本（`history.ts` 注释）。手机上 `device-sync.json` 已经因此长到十几 MB，并且在 JS 线程里解析。会话量通常远大于正文，放进现有条目会让它成倍增长。
- 现有规则里，删除文件要用户“采用”才生效，两端都改过同一文件会产生冲突卡片。会话的删除、重写和续聊都很频繁，照搬这些规则会让同步页堆满待处理项。

**结论**：不能把会话作为现有条目的附带文件，也不宜新增一个普通 kind。需要独立通道 + 交换格式 + 专用合并规则。

## 3 设计决定（2026-10-12 已确认）

| # | 问题 | 推荐 | 备选 |
| --- | --- | --- | --- |
| D1 | 会话放在哪里同步 | 独立的「对话通道」：远端放在 `devices/<deviceId>/conversations/`，共用内容包、WebDAV 传输和同步按钮，不进入作品提交记录 | 新增 kind `conversation` 进入现有引擎：复用最多，但旧版本整体失败、同步状态膨胀，否决 |
| D2 | 默认是否开启 | 默认关闭；在「同步范围 → 对话记录」按作品开启，组头可一键全开 | 默认跟随作品开启：老用户首次升级后可能一次下载几百 MB |
| D3 | 同步哪些内容 | 正文、思考、工具摘要（名称/状态/输入与结果摘要）、提案摘要、子智能体摘要、压缩摘要、模型标识；不同步草稿、审批/温度设置、附件正文与图片、评测快照、完整工具参数和差异块 | 只同步正文：最简单，但另一端看不到过程 |
| D4 | 删除与恢复 | 删除会话传到另一端：电脑端归档（可在「已归档会话」恢复），手机端删除；在电脑端恢复后，手机重新收到 | 删除只在本机生效：远端会话会在下次同步时“复活”，不推荐 |
| D5 | 两端同时续聊同一会话（中间没同步） | 两段都保留，按父消息排成先后两段，不报冲突 | 拆成两个会话：更干净，但改变会话 ID，提案引用和恢复都更复杂 |
| D6 | 原设备的待审核提案 | 只读显示“在 <设备名> 上待审核”，不能在本端接受；原设备处理后，状态随下次同步更新 | 允许跨端接受：提案基于原设备的正文版本，跨端落盘风险高，否决 |
| D7 | 历史量 | 一期同步所选作品的全部会话；首次下载前显示会话数与大小估计 | 增加「仅最近 N 天」：二期再看实际数据量 |
| D8 | 「初始化本机」 | 本期不做；以后再考虑初始化时一并取回来源设备的会话 | 一期一起做 |
| D9 | 同步到对端的用量 | 随消息只读展示，不计入本机用量统计 | 合并进用量统计：会重复计算 |

## 4 方案

### 4.1 同步单位与身份

- **作品**：用作品在主同步中的键（`book:<portableId>`、`long-book:<bookId>`）。手机按身份文件把本机 `projectId` 换成 `portableId`。作品必须已在本机存在且参与同步，它的会话才会上传或写入；作品暂停、未同步成功或被删除时，会话暂缓，并显示原因。
- **会话**：`sessionId`。两端各自生成，按“作品 + 会话 ID”判重。
- **消息**：`messageId`，在会话内判重。电脑端 ID 只有 32 位随机数，所以导入时如果同一会话里出现同 ID、但来源设备或创建时间不同的两条消息，按冲突处理：后到的一条改成带来源前缀的 ID，两条都保留。

### 4.2 交换格式

两端各自保存一份交换格式定义（桌面 `packages/contracts/src/device-sync/conversation/`，手机 `src/core/device-sync/conversation/`），做法和 `model-config` 一样：严格 Schema、稳定序列化（键排序、无末尾换行）、两端逐字节相同的格式测试。

**会话头** `{ schemaVersion: 1, kind: "deepwrite.conversation-session", id, createdAt, agentTeamMode?, modelConfigId? }`

**消息记录** `{ schemaVersion: 1, kind: "deepwrite.conversation-message", id, role, content, createdAt, status, … }`

| 字段 | 说明 | 电脑 → 交换 | 手机 → 交换 |
| --- | --- | --- | --- |
| `status` | `completed / stopped / error` | 原值 | `complete→completed`、`cancelled→stopped` |
| `errorMessage?` | 字符串 | 原值 | 取 `error.message` |
| `model?` | `{ configId?, provider?, model? }` | `runtime` | `modelConfigId` |
| `thinking?` | 全部思考拼接 | `thinking` | 拼接 `thinking-delta` |
| `steps?` | `thinking / response / tool / compaction` 顺序 | `processingSteps` | `processingSteps` |
| `tools?` | `[{ id, name, status, inputSummary?, resultSummary? }]` | `toolCalls` 截取摘要 | `tool-start / tool-end` |
| `proposals?` | `[{ title, summary, status, additions, deletions, documentTitle? }]`，只读 | `editProposals` 去掉差异块、正文和快照 | 从提案库读取对应记录的摘要 |
| `subagents?` | `[{ name, status, summary?, output? }]`，只读 | `subagentRuns` | 子智能体进度事件 |
| `compactions?` | `[{ id, summary, createdAt }]` | `contextCompactions[].checkpoint` | 无 |
| `attachments?` | `[{ id, name, kind, mediaType, size }]`，只有元数据 | 原值 | 去掉正文和图片引用 |
| `usage?` | 只读展示 | `usage` | 无 |
| `runId?` | 原值 | 原值 | 原值 |

不进入交换格式的字段：`draft`、`approvalMode`、`temperature`、`evaluationSnapshot`、`retry`、`activityOnly`、`contextTokens`、完整工具参数、提案差异块与 `proposedText`、`discardSnapshot`、`generationTarget`、`appendedAt`。

**写入本机时**，交换记录转换成本机消息，另外附加一个可选字段 `remote: { recordHash, deviceName, proposals?, subagents?, compactions? }`（两端的消息类型各加一个可选字段，手机严格 Schema 同步放宽）。界面用 `remote` 里的只读部分显示提案和子智能体卡片，所有操作按钮禁用，并标注来源设备。

**只由原设备修改**：同步来的消息在本机不会被修改（可以删除，也可以被重写操作移出会话）。所以重新导出时，这些消息直接引用原来的 `recordHash`，不需要从本机格式反向转换，也不会因为转换有损而导致两端来回改写。

### 4.3 合并规则

合并只取并集，加上显式删除标记，没有冲突状态：

- **会话集合** = 各设备会话的并集。某个会话在一端不存在，不代表删除。
- **会话删除/恢复**：每个会话有 `{ deleted, at }` 状态，按时间最新者为准（时间相同时比较设备 ID）。电脑端把删除落为归档，彻底清除也只发出删除；手机端落为删除。
- **消息集合** = 会话内各设备消息的并集，减去“已移出”标记。
- **消息顺序**：清单里每条消息记录 `parentId`（前一条消息）。合并时按父消息建链：正常情况下就是原顺序，不受两台设备时钟偏差影响；两端同时续聊时，同一父消息下有两个分支，按分支首条的创建时间先后，把两段依次排下去（D5）。
- **重写**（「修改并重新发送」）：被移出的消息记为 `removed: [{ id, at }]`；之后新发的消息照常加入。
- **消息更新**：只有原设备会更新自己的消息（例如提案从待审核变为已接受）。接收端按清单里的 `at` 用最新记录替换，并更新 `remote.recordHash`。
- **只导出已结束的消息**：正在生成的消息不导出；会话导出到最后一条已结束消息为止，剩余部分等下次同步。

### 4.4 远端布局与传输

```text
spaces/<spaceId>/objects/<hash前两位>/<packHash>.json                       # 共用：消息记录、会话头、清单都放在内容包里
spaces/<spaceId>/devices/<deviceId>/head.json                                # 不变：作品同步
spaces/<spaceId>/devices/<deviceId>/commits/…                                # 不变
spaces/<spaceId>/devices/<deviceId>/conversations/head.json                  # 新增：对话通道引用
spaces/<spaceId>/devices/<deviceId>/conversations/commits/<分组>/<序号>-<hash>.json   # 新增：对话根清单（不可变）
```

- **三层清单**：根清单 `books: { "<作品键>": 作品清单哈希 }` + `receipts`；作品清单 `sessions: { "<sessionId>": 会话清单哈希 }`；会话清单 `{ header, state, messages: [{ id, parentId, record, at }], removed }`。每层都按内容寻址，没变的子树不重新上传，也不重新下载。新增一条消息只需上传这条记录、一份会话清单、一份作品清单和新的根清单。
- **复用**：WebDAV 传输、受控跳转、限流退避、读回校验、按哈希合包与增量上传、取消、进度条都用现有实现；先上传内容包并读回，再发布 `conversations/head.json`。
- **旧版本不受影响**：旧版本只读取 `devices/<id>/head.json` 和 `commits/`（`engine/remote.ts` 的设备读取），不会进入 `conversations/`。远端目前没有对象清理；以后如果加，必须把对话清单算作引用。
- **大消息**：单个对象受 32 MiB 读取上限约束。记录超过 4 MiB 时，把 `content` / `thinking` 拆成分块对象，记录里只放引用。
- **收据**：根清单的 `receipts` 记录已取回的其他设备根清单哈希，用于显示“对话已取回”；与作品收据分开，互不影响。

### 4.5 本机同步状态

对话通道使用独立的本机状态文件（电脑 `userData/device-sync-conversations.json`，手机 `config/device-sync-conversations.json`），不放进现有的 `device-sync.json`：

- 开启对话同步的作品键（D2 默认关闭，所以用包含列表，与作品的 `excludedKeys` 分开；也不需要修改现有的严格 `syncConfigSchema`，降级时旧版本仍能读取同步配置）；
- 每台远端设备上次处理过的根清单哈希：没变化就跳过；
- 本机导出缓存：`会话 ID → { 本机版本标记, 会话清单哈希 }`。电脑端用会话的 `revision`，手机端用会话的 `updatedAt` 加消息数；没变化的会话不重新转换、不重新计算哈希；
- 不保存任何会话正文副本，所以这份状态不会随历史量增长到 MB 级。

### 4.6 本机写入

**电脑**

- 会话导出和写入都在 Core 进程里完成，经会话存储 worker 读写，使用现有的批次与暂存接口（大消息走 `stage`），沿用 `expectedRevision` 检查。Main 的同步服务通过新增的 Core 命令调用（先在 `packages/contracts` 加命令和 Schema，再接 Main 路由和 Core handler）。
- 同步开始前的 saving 阶段先让 Renderer 刷新待保存的会话；写入后 Main 发出 `conversationHistory.changed { keys }` 事件，Renderer 对空闲作品重新读取历史列表和当前会话。
- 作品的智能体正在运行，或有正在提交的审批时，这个作品的会话本轮暂缓（显示“作品正在生成，稍后同步对话”），其他作品照常进行。
- 新会话写入时 `draft` 为空，`approvalMode`、`temperature` 使用本机默认值；当前会话（`activeSessionId`）不因同步而切换。

**手机**

- 沿用现有规则：生成或受保护写入期间不能同步；同步前先刷新正文和会话。
- 会话写入经 `ProjectConversationRepository`、作品写入队列和 V5 分块存储，不直接写文件；在队列内读出最新会话，合并后保存，然后由现有写入门统一重新加载一次。
- 同步来的会话放进 `history`；如果本机当前会话在另一端有了新消息，就原地追加，不切换当前会话。
- 同步来的用户消息带图片附件元数据但本机没有图片文件，续聊时跳过这张图片并在消息上提示“图片未同步”，不能因读取失败而中断发送。
- 长思考按 `thinking-delta` 的单事件上限拆分。

### 4.7 同步范围与界面

- 两端「同步范围」在「创作空间」后新增「对话记录」分组（桌面 `SyncContentPanel.vue`，手机 `content-panel.tsx`），每行是一个作品，显示会话数；作品本身未参与同步时该行禁用并提示原因。分组的展开、三态全选、乐观勾选、合并保存都沿用现有组件和 `useSyncScope` / `use-scope-draft`。
- 首次开启某作品时显示远端会话数与大小估计（D7），确认后在下一次同步中取回。
- 同步结果增加“对话：上传 N 个会话，下载 M 个会话”；进度条增加“对话记录”阶段，复用现有进度面板。对话通道失败不影响作品同步的结果，单独显示原因。
- 历史列表和消息上标注来源设备（如“来自 手机”）；同步来的提案、子智能体卡片只读。

### 4.8 初始化本机（二期）

预览时列出来源设备上已开启对话同步的作品与会话数，用户勾选后，在作品替换完成后取回会话。会话写入失败不回滚作品替换，可以在下次普通同步时重新取回。

## 5 兼容与版本

- 对话通道是新增目录，旧版本不读取，作品同步照常。两端都升级并开启后才会互通；只升级一端时，界面提示“另一台设备尚未支持对话同步”（判断依据：对方设备目录下没有 `conversations/head.json`）。
- 交换格式带 `schemaVersion`。读到不认识的版本时，只暂缓该作品的对话并提示“需要升级”，不影响其他作品。
- 本机消息新增的 `remote` 字段对旧版本是未知字段：手机旧版本会拒绝读取该会话，所以降级到旧版本不受支持，发布说明里写明。
- 两端格式测试逐字节相同；改动交换格式必须两端同时改、同时发布。

## 6 性能与容量

- 无变化的同步只读取每台设备的 `conversations/head.json`，不下载清单。
- 手机端的转换、哈希和写入都在 JS 线程上执行，所以逐作品处理，作品之间让出线程；只处理根清单里哈希有变化的作品和会话。
- 首次下载一个有几百个会话的作品可能很大：按会话分批写入，每批完成就记录进度，取消后下次从未完成的会话继续。
- 需要实测（合成数据 + 真机）：50 个作品 × 30 个会话 × 100 条消息时的首次上传/下载耗时、手机主线程最长阻塞、本机状态文件大小。

## 7 安全与隐私

- 会话以明文存放在用户自己的网盘上，与正文相同；同步页说明会话里可能包含思考过程和附件名称。
- 评测快照、完整工具参数、附件正文与图片不进入同步，减少外泄面。
- 测试只用 `example.test` 和明显无效的占位凭据，夹具里不放真实对话内容。

## 9 验证计划

- **格式**：两端夹具逐字节相同；严格 Schema 拒绝多余字段、未知版本、超长字段。
- **转换**：用两端真实格式的会话样本（含思考、工具、提案、子智能体、压缩、错误、停止、附件）做“电脑 → 交换 → 手机”和“手机 → 交换 → 电脑”，逐项核对第 4.2 节的映射，确认丢弃项都在清单里。
- **不来回改写**：A 导出、B 写入、B 再导出，引用的记录哈希与 A 相同；连续同步两次，第二次上传和下载都为零。
- **合并**：并集、删除与恢复（按时间）、重写移出、两端同时续聊（父消息分支）、时钟偏差下顺序正确、消息 ID 冲突改名、只导出已结束消息。
- **依赖与忙碌**：作品暂停或未同步时会话暂缓；电脑端运行中的作品跳过；Renderer 收到事件后刷新，未保存的会话不丢；手机端防抖保存不会覆盖刚写入的会话。
- **旧版本兼容**：用旧版本引擎的测试支持读取包含对话通道的同步空间，作品同步结果不变。
- **性能**：请求计数回归（无变化时只读 head）；手机主线程阻塞与本机状态文件大小；大消息分块。
- **桌面运行验证**：Electron 中实际同步、刷新和只读卡片显示（遵守 AGENTS.md 的沙盒启动检测）；手机真机安装包与真实网盘双端往返。类型检查和单元测试不能替代这两项。

## 10 风险与开放问题

- **数据量**：首次下载可能很大。上线前用实际用户数据（只读）估算一次单个作品的会话总量，再决定是否把 D7 的裁剪提前到一期。
- **电脑端并发写入**：Core 写入时 Renderer 可能正在保存同一会话。依靠 `expectedRevision` 拒绝过期批次，并确认 Renderer 收到拒绝后会重新读取，而不是报“保存失败”后丢弃。实现前先读一遍 `persistence-controller.ts` 的冲突处理。
- **手机提案摘要**：手机的提案在单独的提案库里，导出时要按 `proposalIds` 读取，提案库缺失或损坏时只导出消息本身。
- **子智能体详情**：一期只同步摘要和最终输出；如果用户希望在另一端看完整子智能体过程，二期再扩展交换格式。
- **续聊质量**：手机没有上下文压缩，续聊电脑上已压缩的长会话时会按本机窗口截取历史，效果可能和电脑不同。可以考虑二期让手机使用同步来的压缩摘要。

### 11.2 与计划不同或计划未写到的地方

- **收据只看内容**：根清单的收据记录对方 `books` 的哈希，而不是对方提交的哈希。用提交哈希时，两台设备会因为收据变化互相触发新提交，没有尽头；作品同步本来也是这样做的。
- **判断变化只对照“上次确认持有的内容”**：本机状态为每个会话记 `confirmed`（存在/归档/不存在 + 当时的消息 ID）。合并结果没能写入本机时，发布的是本机自己的视图，所以不会把“还没写进来的消息”误判成本机删除。
- **手机写入不走普通保存**：手机普通保存只追加消息（防止旧快照删掉新消息），另一端的删除会被保存逻辑加回来，所以新增了比较指针后整体替换的写法。
- **手机「初始化本机」后忘记本机视图**：D8 本期不带会话，但初始化会清空本机会话；如果不处理，下次同步会把这当成删除并传到电脑。现在初始化成功后清空本机记录的会话，下次同步重新从其他设备取回。“自己发布的作品清单与对方相同就跳过”的捷径也只在本机仍有记录时使用。
- **压缩摘要**只随记录保存，手机不使用，电脑也不把别处的摘要用于本机上下文。
- **用量**随消息只读展示；两端的用量统计都来自运行时事件，同步来的消息不会计入。
- **会话设置不同步**：手机的会话模型、团队模式，电脑的草稿、审批方式和温度都留在本机，新收到的会话使用本机默认值。
